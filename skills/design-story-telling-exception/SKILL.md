# 例外・障害ストーリーテリング検証

「想定外の事態が起きたとき」に、アーキテクチャがどう振る舞うかを **複数の障害ストーリー** で検証します。

## 検証の主な観点

- **耐障害性**: 単一コンポーネントの故障で全体が止まらないか（連鎖故障の遮断）
- **冪等性**: 重複処理されても安全か
- **リトライ・タイムアウト**: 設計に組み込まれているか、無限リトライにならないか
- **サーキットブレーカー・フォールバック**: 外部依存先の障害から保護されているか
- **データ整合性**: 部分失敗でデータが不整合にならないか（補償トランザクション、Saga など）
- **観測性**: 障害が起きたとき、原因特定に必要な情報が取れるか（ログ、メトリクス、トレース、アラート）
- **復旧手段**: 自動復旧 or 手動復旧の手順が設計に存在するか
- **UX**: 障害時にユーザーに伝わる情報・取れる行動が適切か

---

## ステップ1: 入力を読み込む

セッション名がユーザーから渡されていない場合は確認してください。

以下を読み込みます：

- 必須: `~/.claude-utils/session/<session-name>/story-telling-input.md`
- 補助: `~/.claude-utils/session/<session-name>/design-doc.md`（あれば）
- 補助: 関連するコードベース

特に **外部依存先・I/O 境界・状態を持つコンポーネント** を洗い出します。これらが障害ストーリーの主な発生点です。

---

## ステップ2: 障害ストーリーを複数本生成する

**網羅性を重視** して、以下のカテゴリから生成します：

- **外部依存の障害**: 決済 API、メール、サードパーティ認証、CDN、キャッシュ、メッセージキュー
- **インフラ障害**: DB、Redis、ネットワーク、ディスク、メモリ、CPU
- **コンカレンシー問題**: 競合、デッドロック、ロックタイムアウト、二重実行、Race condition
- **データ品質問題**: NULL、文字化け、想定外のフォーマット、巨大ペイロード、過去データ
- **ユーザー起因の異常**: 連打、ブラウザバック、タブ重複、認証切れ中の操作、不正入力
- **時間的な異常**: タイムゾーン跨ぎ、サマータイム、システム時刻ズレ、リクエスト遅延、長時間処理
- **デプロイ・運用起因**: デプロイ中の混在バージョン、マイグレーション中、ロールバック直後

最低でも 5〜8 本。**まず障害ストーリー候補のタイトル一覧をユーザーに提示** し、過不足を確認してから本文に進むことを推奨します。

各ストーリーは以下の形式で記述してください：

```
障害ストーリー <N>: <タイトル>

- 引き金: <何が起きたか>
- 発生コンポーネント: <どこで>
- 進行: <時系列で何が起きるか>
- ユーザーから見た現象: <UI や結果>
- 想定される副作用: <データ・他コンポーネントへの影響>
```

---

## ステップ3: 各障害ストーリーをアーキテクチャに照らす

各ストーリーについて、現状の設計だと「どう振る舞うか」を素直にトレースし、以下を検証：

- 障害は **検知** されるか（タイムアウト、ヘルスチェック、エラー伝播）
- 障害は **隔離** されるか（連鎖故障しないか、サーキットブレーカー）
- **代替手段・フォールバック** はあるか
- **冪等性・補償** は担保されているか（リトライしても二重課金しない、失敗時に元に戻る）
- **観測ログ・メトリクス・アラート** は十分か
- **データ不整合** が起きるなら、回復手段は設計に存在するか
- **ユーザー体験** は壊れすぎていないか（適切なエラー表示、リトライ可能か、進捗が見えるか）

「現状の振る舞い」と「あるべき振る舞い」のギャップを明示することがポイントです。

## ステップ5: フィードバックと改善

- 障害シナリオの過不足を確認
- 特定の領域（例: DB 周り、外部 API 連携）を深掘りしたい要望があれば追加生成
- 修正は同名ファイルを上書き保存

---

## 書き方の注意点

- **「絶対起きない」と思える障害も書く**: 「Redis が落ちる」「DNS が解決できない」など、確率は低くても影響が大きいものは外さない
- **判定は厳しめに**: 「ログが出る」だけで「観測 OK」とせず、「相関 ID で追えるか」「アラートが鳴るか」まで踏み込む
- **解決策を断定しない**: 「サーキットブレーカーを入れるべき」ではなく「現状この障害では連鎖故障する。サーキットブレーカー導入や bulkhead パターンが選択肢として挙がる」のように判断材料を示す
