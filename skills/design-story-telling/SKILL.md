# アーキテクチャ・ストーリーテリング検証スキル（入口）

設計案やアーキテクチャを、抽象的な原理原則（design-policy）ではなく **具体的なストーリーで動かして検証** するためのスキル群です。本スキルはその入口として、以下の役割を持ちます：

- ストーリーテリング検証の **セッションを準備** する（入力の整理・保存）
- 4つの観点の **サブスキルへ誘導** する
- design-policy との **照合のための材料** をセッションに集約する

## 4つの観点（サブスキル）

| サブスキル | 観点 | 主な検出対象 |
|---|---|---|
| `design-story-telling-usecase` | 正常系のユースケース一本道トレース | レイヤー間の責務、データの流れ、API 契約 |
| `design-story-telling-event-storming` | ドメインイベントの時系列 | 境界づけられたコンテキスト、集約、ユビキタス言語 |
| `design-story-telling-exception` | 例外・障害シナリオ | 耐障害性、冪等性、リトライ、フォールバック、観測性 |
| `design-story-telling-user-journey` | 中長期的なユーザー体験 | 体験の連続性、機能間整合性、離脱ポイント、感情曲線 |

各観点ごとに **しっかり時間をかけて見る** ため、サブスキルは独立して呼び出せる構造になっています。本スキル（入口）はあくまで **準備と案内** までを担当します。

---

## ステップ1: 入力を受け取る

ユーザーから以下のいずれかの形で入力を受けます：

- **design-doc スキルの出力**: `~/.claude-utils/session/<session-name>/design-doc.md`
- **口頭での説明**: 「こういうアーキテクチャを考えている」
- **コードベース**: 既存の設計を振り返るケース

情報が不足している場合は、ユーザーに質問して補完してください。特に以下が曖昧な場合は確認が必要です：

- アーキテクチャの全体像（コンポーネント、責務、依存関係）
- 対象とするユースケースや業務領域
- 「これから設計する案」か「既存の設計の振り返り」か

---

## ステップ2: セッション名を決定する

- 既存の design-doc セッションがある場合は、その session-name を **必ず引き継ぐ**（同じセッションにレポートを並べるため）
- 新規の場合は、design-doc と同じルールで自動生成する：
  - 英数字・ハイフン・アンダースコアのみ
  - ケバブケース、要点を表現
  - タイムスタンプ不要

例: `auth-session-improvement`, `payment-flow-redesign`

---

## ステップ3: アーキテクチャ要約を作成・保存する

サブスキルが共通して参照できるよう、アーキテクチャの要約をひとつのファイルにまとめます。design-doc が既にある場合はその内容を抜粋・整形してください。コードベースから補強できる情報があれば追加してください。

### 保存先

```
~/.claude-utils/session/<session-name>/story-telling-input.md
```

ディレクトリが存在しない場合は作成してください。

### フォーマット

```markdown
# ストーリーテリング検証 入力情報

## 対象アーキテクチャ
<タイトル・1〜2行の要旨>

## コンポーネント
- <コンポーネント名>: <責務>

## 主要な依存関係・通信
- <A> → <B>: <目的・プロトコル>

## ユビキタス言語（設計上の用語）
- <用語>: <定義>

## 想定される主要なアクター
- <アクター>: <役割>

## スコープ・対象外
- 対象: <範囲>
- 対象外: <範囲>

## 入力ソース
- <design-doc.md / 口頭説明 / コードベース調査の概要>
```

---

## ステップ4: サブスキルへの誘導

入力情報がそろったら、以下をコンソールに出力してください：

1. **セッション名**: `session-name: <session-name>` の形式（後段スキルへの引き継ぎに使用）
2. **入力ファイルのパス**: `~/.claude-utils/session/<session-name>/story-telling-input.md`
3. **次のアクション案内**:

```
ストーリーテリング検証の準備ができました。
次は以下のサブスキルを呼んでください（順序は任意・全て呼ぶことを推奨）：

1. /design-story-telling-usecase           — 正常系のユースケース検証
2. /design-story-telling-event-storming    — イベントストーミング的検証
3. /design-story-telling-exception         — 例外・障害シナリオ検証
4. /design-story-telling-user-journey      — ユーザージャーニー検証

各サブスキルは ~/.claude-utils/session/<session-name>/ の入力を参照します。
すべて終わったら、design-policy スキルに本セッションのレポート群を読み込ませて
5軸での総合評価ができます。
```

---

## design-policy との関係

本スキル群は、design-policy が示す **5つの抽象的な評価軸** とは独立しています：

- **design-policy**: 設計の原理原則を定性的に評価する（抽象）
- **本スキル群**: 具体的なストーリーで動かして矛盾・盲点を炙り出す（具象）

両者は補完関係にあります。本スキル群は design-policy を内部から呼びません。ユーザーが明示的に design-policy を呼び出し、session 内のレポート群を読み込ませることで、抽象軸と具象事例の往復ができます。

---

## 注意点

- 本スキルは入口・準備までを担当する。**ストーリー生成と検証は各サブスキルで行う**
- セッション名はサブスキル間で共有されるため、必ずユーザーに明示する
- 入力情報が薄いままサブスキルに進むと検証品質が落ちるため、ステップ3で十分な情報を集める
- ユーザーが特定の観点だけを見たい場合は、入口を経由せずサブスキルを直接呼んでもよい（ただし `story-telling-input.md` は事前に整えておく）
