# イベントストーミング・ストーリーテリング検証

設計対象を **ドメインイベントの時系列** として複数のシナリオに分解し、コマンド・イベント・集約・ポリシー・リードモデルの単位でアーキテクチャの整合性を検証します。

## 検証の主な観点

- **境界づけられたコンテキスト (Bounded Context)** の境界が妥当か、漏れ・重複はないか
- **集約 (Aggregate)** の単位が業務トランザクションと整合しているか
- **コマンドとイベント** の対応が明確で、片方向の流れになっているか
- **ポリシー (when X happens, do Y)** が設計のどこに表現されているか
- **イベントの順序・前提条件** が設計に保証されているか
- **ユビキタス言語**: イベント名・コマンド名が業務用語と一致しているか

---

## ステップ1: 入力を読み込む

セッション名がユーザーから渡されていない場合は確認してください。

以下を読み込みます：

- 必須: `~/.claude-utils/session/<session-name>/story-telling-input.md`
- 補助: `~/.claude-utils/session/<session-name>/design-doc.md`（あれば）
- 補助: 関連するコードベース（必要に応じて）

特に **既存のドメイン用語・集約候補・イベント候補** を抽出しておきます。これらがシナリオの素材になります。

---

## ステップ2: イベントストーミング・シナリオを複数本生成する

**網羅性を重視** して、以下の単位でシナリオを生成します：

- **主要なドメインプロセスごと**: 注文プロセス、認証プロセス、決済プロセス、退会プロセスなど
- **イベントの分岐ごと**: 成功パス／失敗パス／代替パス
- **時系列の長さ**: 短期（1リクエスト内）／中期（数分〜数時間）／長期（複数日にまたがる、状態を持ち続ける）

最低でも 3〜5 本のシナリオ。**まずシナリオ候補のタイトル一覧をユーザーに提示** し、過不足を確認してから本文に進むことを推奨します。

各シナリオは以下の形式で記述してください：

```
シナリオ <N>: <タイトル>

時系列イベント列:
1. [Command] <コマンド名> on <Aggregate>
   → [Event] <イベント名>
2. [Policy] When <イベント名>, then <反応>
3. [Command] <...> on <Aggregate>
   → [Event] <...>
4. [Read Model] <リードモデル名> updated

関与する Bounded Context:
- <BC1>
- <BC2>

業務上の達成: <この時系列が達成すること>
```

凡例：
- **Command**: ユーザーまたはシステムからの「やってほしい」依頼
- **Event**: 起こったこと（過去形・事実）
- **Policy**: イベントを受けて自動的に走る反応
- **Read Model**: クエリ用の投影
- **Aggregate**: 整合性境界

---

## ステップ3: 各シナリオをアーキテクチャに照らす

書き出したイベント列を、`story-telling-input.md` のコンポーネント・責務と突き合わせて、以下を検証：

- 各 **コマンド** を受ける担当コンポーネントが存在するか、責務に矛盾はないか
- 各 **イベント** を発行する主体が決まっているか、誰が受け取るかも明確か
- **集約** の境界が、コマンド／イベントの粒度と整合しているか（同一トランザクションで複数集約を更新していないか等）
- **境界づけられたコンテキスト** をまたぐ通信が、適切な統合パターン（共有カーネル／公開ホストサービス／アンチコラプションレイヤーなど）になっているか
- **ポリシー** が設計上「どこかのコンポーネント」に明示的に存在するか、暗黙のままになっていないか
- **イベント名・コマンド名** がユビキタス言語と一致しているか（CRUD的な「Update」になっていないか）

## ステップ5: フィードバックと改善

- シナリオの過不足についてユーザーに確認
- 集約境界・BC 境界の議論に踏み込みたい場合は追加検証
- 修正は同名ファイルを上書き保存

---

## 書き方の注意点

- **イベントは過去形で書く**（「注文された」「在庫が引き当てられた」）。命名がCRUDになっている場合は、業務語彙への置き換えを提案する
- **シナリオの長さに偏らない**: 短期処理だけ、長期処理だけにせず、両方の時間軸でアーキテクチャを揺さぶる
- **集約・BC 境界の指摘は根拠とセットで**: 「この集約は分けるべき」ではなく「このシナリオでは X と Y を同一トランザクションで整合させる必要がないように見える、その場合は集約を分ける選択肢がある」のように
