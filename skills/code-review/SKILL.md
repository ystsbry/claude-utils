# コードレビュー生成スキル（code-review）

実装者へのリスペクトを基本姿勢に置きつつ、確認事項・良い点・サマリーまでを含む実用的なレビューコメントを生成します。生成結果はセッションに保存され、ユーザーとの対話を通じてブラッシュアップできます。

## 基本姿勢

- **実装者へのリスペクト**を最優先にする。揚げ足取りや上から目線の指摘はしない
- 不明点は**断定せずに「確認させてください」**と尋ねる形で書く
- 良い点は意識して拾い上げる（「直すべき点」だけのレビューは実装者の心理的安全性を損なう）
- 致命的な問題と軽微な提案を区別し、ラベル付けする
- 実装者が選んだ意思決定の背景を尊重する。代替案を出すときは「こういう選択肢もある」というトーンで

---

## ステップ1: 入力を受け取る

ユーザーから以下を受け取ります：

### 1-1. レビュー対象（必須）

以下のいずれかの形式で指定される：

- **GitHub PR 番号 / URL**（例: `#123`, `https://github.com/org/repo/pull/123`）
  - `gh pr view <番号> --json ...` や `gh pr diff <番号>` で内容を取得
- **ブランチ差分**（例: `feature/foo を main と比較`）
  - `git diff <base>...<head>` で差分を取得
- **特定のファイルパス・コミット**
  - `git show <commit>` や `git diff <commit>^..<commit>` で取得
- **未コミットの変更**
  - `git diff` / `git diff --staged` で取得

入力が曖昧な場合は、対象が何かをユーザーに確認すること。

### 1-2. レビュー観点（任意）

ユーザーは以下のいずれかの形でレビュー観点をまとめたマークダウンを渡してくる可能性がある：

- **ファイルパス**: `path/to/review-checklist.md`（このファイルを Read で読み込む）
- **本文の貼り付け**: プロンプト内に直接マークダウンが含まれている
- **省略**: 観点指定なし。汎用的なレビュー観点で進める

観点が指定された場合は、それを**最優先**でレビューに反映する。指定されていない場合は、後述の「デフォルトのレビュー観点」をベースにする。

---

## ステップ2: 差分を確認する

レビュー対象に応じて以下のコマンドで差分を取得する：

```bash
# PR の場合
gh pr view <番号> --json title,body,files,baseRefName,headRefName,author,state,additions,deletions
gh pr diff <番号>

# ブランチ差分の場合
git diff <base>...<head>
git log <base>...<head> --oneline

# 未コミットの場合
git diff
git diff --staged
git status
```

差分が大きい場合は、変更ファイル一覧とサマリーを先に把握し、重要そうなファイルから順に詳細を読む。

---

## ステップ3: 観点を整理する

### ユーザーが観点マークダウンを渡した場合

その観点を読み込み、各観点に対して差分を照らし合わせる。観点に書かれていない項目について深掘りはしないが、**明らかな致命的問題**（セキュリティ・データ破壊など）に気づいた場合はサマリーで触れる。

### 観点指定がない場合のデフォルト観点

以下を汎用観点として用いる：

| 分類 | 観点 |
|---|---|
| **正しさ** | ロジックは仕様通りか／エッジケース・境界条件の扱い／例外処理 |
| **セキュリティ** | 入力検証／認可チェック／秘密情報の漏洩／インジェクションリスク |
| **可読性** | 命名／関数・モジュールの責務／コメントの過不足 |
| **保守性** | 既存コードとの整合性／重複／拡張性／テスタビリティ |
| **テスト** | テストの有無・粒度／カバレッジの妥当性／ハッピーパス以外のケース |
| **パフォーマンス** | N+1／不要なループ・コピー／ホットパスの計算量 |
| **後方互換性** | 既存 API・スキーマへの影響／マイグレーションの要否 |

すべての観点を均等に扱う必要はない。差分の性質（バグ修正・新機能・リファクタなど）に応じて重みを変える。

## ステップ4: レビューを生成する

### 出力フォーマット

```markdown
# コードレビュー: <レビュー対象のタイトル>

## 判定

LGTM / Comment / Request Changes <!-- いずれか一つ -->

<!-- 判定の一行コメント。「概ね問題なし」「いくつか確認したい点あり」など -->

## 実装者へのコメント

<実装お疲れさまでした、というトーンで始める。実装者がどんな意思決定をしたかを汲み取り、それに対する敬意を示す。1〜2 段落>

### 確認させてください

<!-- 確認事項がある場合のみ。なければこのセクションごと省略 -->

1. **<確認したい点1>** — `path/to/file.ts:123`
   <なぜ確認したいか・どう答えてほしいかを簡潔に>

2. **<確認したい点2>** — `path/to/file.ts:456`
   <同上>

### 提案（任意対応）

<!-- マスト修正ではなく、選択肢として伝えたい改善案。なければセクションごと省略 -->

- **<提案1>** — `path/to/file.ts:789`
  <提案内容と、現状でも問題ない理由>

## 良い点

<!-- 必ず1つ以上書く。表面的な褒めではなく、具体的に何が良かったかを書く -->

- **<良い点1>** — `path/to/file.ts:12`
  <なぜ良いと思ったか。設計判断・リーダブルさ・テストの網羅性など>

- **<良い点2>** — `path/to/file.ts:34`
  <同上>

## まとめ

<2〜4 行。判定の根拠、確認事項の温度感、マージ可否の見立てを実装者に伝わる形で>
```

### 各セクションの書き方

#### 判定

- **LGTM**: マージしてよい。確認事項があっても軽微で、実装者の判断に委ねられるレベル
- **Comment**: マージ前に確認したい点がある。ブロックするほどではないが、回答を待ちたい
- **Request Changes**: 致命的な問題があり、修正が必要

判定理由を一行で添える。

#### 実装者へのコメント

- 「実装お疲れさまでした」「〜を考慮されているのが伝わります」のような開きで始める
- 実装者の意思決定（採用したアプローチ・トレードオフ）を**読み取り、汲み取った形**で書く
- お世辞にならないよう、具体に踏み込む

#### 確認させてください

- **断定しない**。「これは間違っています」ではなく「〜の意図を教えていただけますか」「〜の場合の挙動はどうなりますか」
- ファイルパスと行番号を必ず添える
- 確認事項がない場合はセクションごと省略する

#### 提案（任意対応）

- 「マスト修正ではない」ことを明記する
- 「現状でも問題ないが、〜という選択肢もある」というトーン
- 提案がない場合はセクションごと省略する

#### 良い点

- **必ず 1 つ以上書く**。良い点が見つからないレビューは存在しない
- 「コードがきれい」のような曖昧な褒めではなく、**具体的に何がどう良いか**を書く
  - 例: 「`UserRepository` に副作用を閉じ込めている設計が、テスタビリティと将来の差し替え可能性の両方に効いている」
- 良い設計判断・リーダブルなコード・適切なテスト・親切なコメントなど、なんでもよい

#### まとめ

- 判定の根拠を簡潔に
- 確認事項の温度感（「マージ前に必ず」「次の PR でもいい」など）
- 実装者がどう動けばよいかが伝わるように

## ステップ5: ファイル保存とコンソール出力

### セッション名の決定

レビュー対象から、ファイルシステムに適した短いセッション名を自動生成する：

- **PR の場合**: `review-pr-<番号>-<タイトル要点>`（例: `review-pr-123-add-auth`）
- **ブランチの場合**: ブランチ名をベースに（例: `review-feature-coupon`）
- **コミット・ファイルの場合**: 内容を要約したケバブケース（例: `review-fix-lock-contention`）

英数字・ハイフン・アンダースコアのみ。タイムスタンプは不要。

### 保存先

```
~/.claude-utils/session/<session-name>/code-review.md
```

ディレクトリが存在しない場合は作成する。

### 観点マークダウンを受け取った場合の保存

ユーザーが渡したレビュー観点もセッションに保存しておく（後の対話で参照しやすくするため）：

```
~/.claude-utils/session/<session-name>/review-perspectives.md
```

ファイルパスで渡された場合は内容をコピー。本文で渡された場合はその本文を保存する。

### コンソール出力

ファイル保存後、以下をすべてコンソールに出力する：

1. **セッション名**: `session-name: <session-name>` の形式
2. **保存先パス**: `~/.claude-utils/session/<session-name>/code-review.md`
3. **レビュー本文の全文**: 生成したマークダウンをそのまま出力する（実装者にそのまま渡せる形）

---

## ステップ6: フィードバックと改善

レビューを提示した後、ユーザーは以下のような形でブラッシュアップを依頼してくる：

- 「もう少しソフトな表現にして」
- 「`X` の確認事項は不要、削って」
- 「セキュリティ観点をもっと深掘りして」
- 「良い点をもう少し具体的に」
- 「Request Changes ではなく Comment に変えて」

依頼に応じて：

1. レビュー本文を修正する
2. **同じセッション名のファイルを上書き保存する**
3. 修正版の全文を再度コンソール出力する

セッション内に複数の review-*.md ができないように注意する（PR ごとに 1 ファイル）。

---

## 注意点

- ユーザーが渡したレビュー観点マークダウンは**勝手に編集しない**。観点を増やしたい場合はユーザーに提案する形で
- 差分が非常に大きい（数千行を超える）場合は、すべてを精緻にレビューするのではなく、**重要なファイルから順に見て**、見きれない範囲は明示する（「`migrations/` 配下は規模が大きいため目視確認のみ」など）
- セキュリティ・データ破壊・後方互換性の重大な懸念は、観点指定の有無に関わらずサマリーで必ず触れる
- 実装者の人格や能力に踏み込むコメント（「ここは経験不足を感じます」など）は絶対に書かない。コードと事実にのみ言及する
- 「絶対」「明らかに」のような強い言葉は最小限に。事実ベースの根拠を添える
